# Flutter + serious_python spike

Throwaway proof-of-concept for the UI direction in
`docs/` (see the "Cross-platform UI direction" decision record). Not part of
the app — this proves one thing: that `trenchchat/core/identity.py` and
`trenchchat/core/storage.py` can run unmodified inside a Flutter app via
`serious_python`, on-device. Nothing here is wired into `trenchchat/`.

## What it does

`python/app/main.py`:

1. Starts a sandboxed `RNS.Reticulum` instance (its own config dir, not
   `~/.reticulum`).
2. Constructs a `trenchchat.core.identity.Identity`, then constructs a second
   one pointed at the same path to prove the keypair round-trips through
   disk.
3. Opens a `trenchchat.core.storage.Storage` (plain SQLite, no SQLCipher —
   see "Known gap" below), writes one row with `upsert_server`, reads it back
   with `get_server`.
4. Writes `result.json` (pass/fail per step) next to the databases.

`lib/main.dart` runs that script via `SeriousPython.run(sync: true)` and
displays `result.json` in a single-screen UI.

## Before building: vendor the core package

`trenchchat/core/` isn't pip-installable, so it has to be copied into the
Python app bundle before packaging. Run one of:

```bash
./prepare.sh          # Linux/macOS
```
```powershell
.\prepare.ps1          # Windows
```

from this directory. It copies exactly the modules `identity.py` and
`storage.py` transitively need — `trenchchat/__init__.py`, `config.py`,
`core/__init__.py`, `core/fileutils.py`, `core/lockbox.py`,
`core/permissions.py`, `core/identity.py`, `core/storage.py` — into
`python/app/trenchchat/`. Re-run it after pulling upstream changes to those
files.

## Building

Requires the Flutter SDK and, for Android, the Android SDK/NDK — neither is
installed in this environment, so this has not been built or run yet. This
directory has app-level files only (`pubspec.yaml`, `lib/`, `python/`); the
platform scaffolding (`ios/`, `android/`) doesn't exist yet because it's
generated by the Flutter SDK, not hand-written. First command on a machine
that has Flutter:

```bash
flutter create --project-name trenchchat_spike .
```

This is a repair/scaffold operation, not a template stamp — by default (no
`--overwrite` flag) it only creates files that are missing and leaves
`pubspec.yaml` and `lib/main.dart` alone, so it's safe to run on top of what's
already here.

Then:

```bash
./prepare.sh
flutter pub get
dart run serious_python:main package python/app -p iOS --python-version 3.12 \
  -r rns==1.4.2 -r lxmf==1.1.1 -r msgpack==1.1.2 -r cryptography==43.0.1 -r cffi==2.0.0
flutter run -d <ios-simulator-or-device>
```

Those five `-r` pins are **not** `requirements.txt`'s desktop pins — they're
deliberately different, and that's the point of the next section. Double-
check `dart run serious_python:main package --help` for the exact current
flag names (`--python-version` vs. something else) before relying on this
command verbatim; CLI flags are the one thing here I couldn't fetch a
canonical source for.

iOS needs Xcode, which only runs on macOS — that's a hard platform
requirement independent of Flutter or serious_python, so this leg can only
run on a Mac. Android is the same shape, swapping `-p iOS` for `-p Android`
and needing the Android SDK/NDK instead of Xcode.

## Known gap found during research (see decision record, risk #1)

Checked `pypi.flet.dev` directly (the wheel index `serious_python`/Flet uses
for binary packages) rather than trusting its docs page's summary table:

| Package | iOS wheel confirmed on `pypi.flet.dev`? | Version(s) seen |
|---|---|---|
| `rns`, `lxmf` | N/A — pure Python, no compiled deps | any |
| `cryptography` | Yes, for cp312/cp313 | `43.0.1` (build tag `10`) — **not** `46.0.5`, `requirements.txt`'s pin |
| `cryptography` | Yes, for cp314 | `48.0.0` |
| `cffi` | Yes, for cp312/cp313/cp314 | `1.17.1` or `2.0.0` |
| `msgpack` | Yes, for cp312/cp313/cp314 | `1.1.2` — matches `requirements.txt` exactly |
| `Pillow` | Yes (per flet.dev's docs table; not independently re-checked against the raw index) | `12.2.0` / `11.1.0` / `10.4.0` |
| `sqlcipher3` | **No** — not on the index, no known recipe | — |

`serious_python` 4.5 can embed Python 3.12, 3.13, or 3.14 (`--python-version`
flag); the wheel builds above are keyed to that choice, so the mobile build's
`-r` pins have to match whichever Python version gets selected. This is a
real, permanent divergence from `requirements.txt`, not a temporary gap to
close: the desktop app can keep `cryptography==46.0.5` since PyPI has a
normal wheel for it, while the mobile build is pinned to whatever version
`pypi.flet.dev` has actually built (`43.0.1` for cp312/cp313 as of this
check). Confirm current versions before every mobile build — this index is
maintained separately from PyPI and moves independently.

Everything `identity.py` and `storage.py` need in **plain** (no-PIN,
unencrypted-DB) mode is covered. `sqlcipher3` — needed only when a PIN is set
(`Storage(encryption_key=...)`) — has no prebuilt mobile wheel and no known
`python-for-android` / Mobile Forge recipe as of this check. At-rest
encryption on mobile needs its own follow-up (a custom Mobile Forge recipe
that cross-compiles SQLCipher + `sqlcipher3`, or a different at-rest
encryption approach for the mobile build specifically) before the PIN-lock
feature can port. This spike deliberately runs `Storage` unencrypted to stay
inside the currently-covered set.

## What still genuinely needs a device, vs. what was just unverified paperwork

Two different kinds of "unverified" were mixed together in an earlier pass of
this doc; splitting them out:

**Resolvable by research, now done:** the `serious_python` version pin, which
dependency versions actually exist as iOS wheels, and whether
`flutter create` is safe to run on top of these files. All confirmed above
and reflected in the pinned versions and commands — nothing here still needs
a Mac to answer.

**Only answerable by actually building and running on the target runtime:**
- Whether `trenchchat.core`'s use of threading/sockets (via RNS) behaves the
  same inside serious_python's embedded interpreter as it does under desktop
  CPython — sandboxed filesystem and iOS's threading restrictions are real
  differences, not just packaging friction.
- iOS background execution (risk #2 in the decision record) — whether
  Reticulum's interfaces and any open Links survive iOS suspending the app.
- Generic build-toolchain mechanics (codesigning, CocoaPods linking the
  cross-compiled wheels) — likely to produce noise unrelated to the
  architecture question, but only discoverable by running the build.

## Result

The Flutter/iOS build itself hasn't run — no Flutter SDK, Android SDK, or
Xcode on this machine, and iOS specifically requires a Mac categorically.
What has been verified: `python/app/main.py`, running against the vendored
`trenchchat/core` copy under plain desktop Python (not on-device), produces
four `"ok": true` steps — Reticulum init, identity creation, identity reload
from disk, and a storage write/read-back all succeed unmodified. This
confirms the script and the core code it drives are correct; it does not
confirm the two runtime-only items in the section above, which is what
running this on a Mac will actually settle.

One real constraint surfaced while writing this: `Identity.__init__`
constructs an `RNS.Destination`, and `RNS.Transport` only allows one
`Destination` registration per identity hash + aspect *per process*.
Constructing a second `Identity` wrapper for the same on-disk key in the same
process (as an early version of this script did, to prove the disk round
trip) raises `KeyError: Attempt to register an already registered
destination`. Not a bug — `main.py` only ever builds `Identity` once per run
— but worth knowing if a future bridge/test harness ever wants to
re-instantiate `Identity` mid-process instead of once at startup.
